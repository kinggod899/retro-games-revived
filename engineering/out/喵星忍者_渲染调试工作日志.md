## 三、根因定位过程（b93 → b132）

### 3.1 第一次误判：认为 native glDrawArrays 无效

b93 把 `glDrawArrays` 换成 `glClear` 仍全红 → 误判"顶点/纹理内容有问题"。
b98 同实验全红 → 但 b96/b97 已证 glClear 有效，**该实验无法区分**，只能证明"换成 glClear 也是红"。

### 3.2 Java GL10 桥接尝试（b102-b125，最终否定）

方案：patch `libwiengine.so` 的 8 个 GL GOT 槽，重定向到 `libaal.so` 内的 `br_*` 函数，由 `br_*` 用 JNI 调 Java 侧 `Director.getInstance().gl`（GL10）。

关键突破：
- **b113**：`aal_br2.c`（21944B）首次让进程稳定，日志 `patch: 8 GOT slots redirected` + `fetch_gl obj=0x35` + `bridge_init ok en=1 dis=1 bind=1 vert=1 tc=1 draw=1 wrap=1`
- **b116-b120 崩溃史**：
  - b116 `FloatBuffer.wrap(float[])` 是 heap buffer，`GetDirectBufferAddress` 返回 NULL → `glUtilsPackPointerData+112` fault 0x0
  - b117 改 `NewDirectByteBuffer` 后 `g_v[16]` 仅 64B，encoder 按 count 读 ~0x608B → SEGV_ACCERR
  - b118/b119 加 `br_glDrawElements` → 崩在 `/system/lib/arm/nb/libtcb.so`（houdini 转译码）
  - **b121 突破**：`br_glVertexPointer/br_glTexCoordPointer` 改为**不 memcpy，直接 `NewDirectByteBuffer(env, ptr, 4096)` 透传原始 ARM 指针** → 723 帧无 FATAL
- **b125 决定性否证**：在 `br_glDrawArrays` 内通过 Java GL10 调 `glClearColor(0,0,1,1)+glClear(0x4000)`，日志 `DA blue clear sent` 但截图**仍全红**
  → **从 ARM native 经 JNI 调 Java GL10 的路径，encoder 的绘制完全不写显示 surface**（houdini `libtcb.so` 占用 TLS，encoder 上下文不可达）

**Java GL 桥接方案就此否定。**

### 3.3 br_ 改为 native 透传 + TI 修正（b126-b131）

`aal_br2.c` 大改版：
- `struct gotslot` 加 `orig` 字段并去掉 `const`；`patch_got` 覆写前把 `*slot` 原值存入 `g_slots[i].orig`
- 所有 `br_*` 改为通过函数指针调原始 native 函数（`typedef fn_1i/fn_2i/fn_3i/fn_vp/fn_da/fn_ti/fn_gt` + `ORIG(i)` 宏）
- `br_glTexImage2D` 检测 `w<=0||h<=0` 时用 `scaleImage` 记下的 `g_siW/g_siH` 修正

崩溃与修正：
- b130 `TI FIX 0x0 -> 512x256 (si=480x210)` → SIGSEGV fault 0xca43ffd9。根因：ptr 缓冲只有 480×210×4=403200B，encoder 按 512×256×4=524288B 读越界。**nextPow2 尺寸大于源数据缓冲，不能用**
- b131 改用 `g_siW/g_siH`（480×210）→ 稳定无 FATAL，`TI w=480 h=210`

### 3.9 UV NaN 机理

`wyGLTexture2D::draw @0xb1824-0xb18ec`：
```
0xb1852 ldr r0,[r4,#0x6c]      ← 读纹理 width 成员

0xb1858 blx 0x10fac4           ← __floatsisf

0xb1870 blx 0x10fd08           ← __divsf3，用 (float)(width*2) 作除数
```
`width=0` → 除零 → inf/nan → UV NaN → quad 采样 NaN → 不可见。

## 九、ARM Thumb 逆向踩坑记录（重要，后续别再犯）

1. `.ARM.exidx` 的 PREL31 需 `&0x7ffffff` 才得到真实 vaddr
2. PLT 是 ARM 模式 12 字节 stub，header 20 字节，入口 = `.plt+20+i*12`，i 按 `.rel.plt` 顺序（**不是 .dynsym 索引**）
3. capstone `ARM_REG_PC=11` 不是 15
4. Thumb `ldr rX,[pc,#imm]` 的 imm 是 `imm8*4`，base = `Align(ins+4,4)`
5. 符号名不是直接 pool，而是 `ldr r1,[pc,#imm]` 取 pool 里的 PC 相对偏移，再 `add r1,pc` 才得字符串地址
6. `movs r3,#0` 的 2 字节编码不可靠（`0x0023` 解成 `movs r3,r4`），要用 `mov.w r3,#0 = 4f f0 00 03`
7. `movs Rd,#imm3` T1 编码 = `000 11 imm3 Rd`（`0x0020`=movs r0,#0、`0x0022`=movs r2,#0）；T2 imm8 = `001 00 Rd imm8`（`0x2009`=movs r0,#9、`0x0320`=movs r0,#3）
8. `lsls r0,r0,#3` 编码 = `0x00C0`（bytes `c0 00`），**不是** `00 03`
9. `const/4` 字面量必须在 -8..7；`const/high16` 要求低 16 位为 0
10. smali `fill-array-data` 与 `array-data` 元素数必须精确匹配
11. dalvik 合并分支后类型污染，必须用不冲突寄存器且避免 if 分支
12. `glGetError` 是接口方法，必须 `invoke-interface`；`invoke-static` 会 `IncompatibleClassChangeError`
13. BL 编码：`aligned=(ins+4)&~3; off=target-aligned; hw=off//2; S=1 if hw<0 else 0; imm10=(hw>>11)&0x3FF; imm11=hw&0x7FF; J1=S; J2=S; hw1=0xF000|(S<<10)|imm10; hw2=0xC000|(J1<<13)|(J2<<11)|imm11`
14. `enc_blx(0xb19da,0x726bc)` 应精确复现原始字节 `c0f770ee`
15. **切片赋值必须等长**：`so[0xa:0xb]=4字节` 会删字节导致 `dlopen undefined symbol JNI_OnLoad`
16. houdini 下 ARM so 的代码段在 `/proc/self/maps` 里是 **`r--p` 不是 `r-xp`**；基址 = 含 `libwiengine.so` 且 file offset 为 `" 00000000 "` 的第一行
17. `libwiengine.so` 的 `.bss` 只映射 4KB（filesz 到 0x13f004，memsz 到 0x185b54），**访问 0x13f004 之后的 .bss 会 SEGV_ACCERR**
18. `setEnv` 签名是 `void setEnv(void* arg, void* reserved)`，**arg 是 `JNIEnv*`**（内部 `GetJavaVM` 取 `JavaVM*`），不是 `JavaVM*`
19. `wyUtils::getNextPOT` = `0xcad94`；`__floatsisf`=0x10fac4；`__divsf3`=0x10fd08；`__mulsf3`=0x10f92c
20. `FloatBuffer.wrap(float[])` 是 heap buffer，`GetDirectBufferAddress` 返回 NULL；必须用 `NewDirectByteBuffer`

## 5. 根因定案（b144）

四条 `512×512` 上传的原始 ptr 前 8 字节**全部是 0**：

```
TX144 orig n=0 type=0x1401 ptr=0xc2878940 bytes=0000000000000000
TX144 orig n=1 type=0x8033 ptr=0xc21a1bc0 bytes=0000000000000000
TX144 orig n=2 type=0x1401 ptr=0xc21f3040 bytes=0000000000000000
TX144 orig n=3 type=0x1401 ptr=0xc34a9340 bytes=0000000000000000
```

替换成纯青后，屏幕从 `(255,0,0,255) x2110139 = 81.41%` 变成 `(0,255,255,255) x2371913 = 91.51%`，`cyan=2373518`、`red=0`，diff b142→b144 变化 `2386457` 像素、bbox `[96,0,2399,1035]`（整个游戏 surface）。`DIAG144 bind n=0..5 tex2d=1 active=0x84c0 glErr=0`、`GT ids=2,3,1`、`BT n=1..60` 全 `t=0xde1`。

矛盾点在这里：AAL 的 `scaleImage` 明明解码成功（`SI alpha stats total=100800 nz=36404 a0=64396 a255=31995`、`SI direct copy done` 4 次），可 native 拿去 `glTexImage2D` 的缓冲区却全 0。日志给出尺寸错位：

| AAL 写入的 bitmap | native 上传 |
|---|---|
| `480x210` / `512x256` / `800x51` / `800x480`，`stride=1920` 等 | `TI w=512 h=512` 全 4 次，`inf=6408`、`type=5121/32819` |

**定案**：`wyGLTexture2D::initSize @0xaf540` 的 isize 补丁把 `[r4,#0x6c]/[r4,#0x70]` 固定为 512（消除了 UV 除零 NaN），`doLoad @0xb0eec` 于是按 512×512 分配并 `lockPixels` 出一块上传缓冲区；而 AAL `scaleImage` 解码后写的是自己那块真实尺寸 bitmap（`SI direct copy done` 只说明 AAL 内部两块尺寸相同）。**两块内存不是同一块**，AAL 的像素从未落到 native 上传的缓冲区 → 上传全 0 → 采样 `(0,0,0,0)` → 黑块 / 全透明。这也解释了 b137「注入 quad 仍无画面」和 b141「修了 alpha 仍红」：几何和 blend 都修了，纹理内容始终是空的。

b144 同时证成：纹理对象绑定正确（`tex2d=1`、`active=GL_TEXTURE0`）、采样链通、`glGenTextures/glBindTexture` 正常、全屏 quad 一直在画（`VP sz=2 [0 0 2304 | 0 0 1036 | ...]` + UV 0..1），只是纹理全 0 才看不见。**只要把真实像素送进上传缓冲区，画面会立刻出现。**

### 16.1 图集层（位图文字）

资源 `res/drawable/ui_en.png` + `res/raw/ui_en.plist`，帧坐标/尺寸/rotated/sourceSize 一律不动，只重绘像素。生成器 `<WORKSPACE>\out\_lang\_gen.py` → `ui_cn.png`。

三个关键算法（反复试错收敛出来的，换写法就崩）：

1. **文字掩码 `textmask(a)`**：`op=al>140`；bbox 内不透明像素按亮度 28 级量化，占比 ≥8% 的前 3 个簇作为底板色（refs）；`core=op & (((sat>0.42)&(lum>78)) | (lum>216) | (dmin>100))`；再 `mxf(3)` → `mxf(5)` 形态学闭运算；黑描边 `dk=(lum<56)&op&mxf(core,9)`；最终 `mnf(mxf(m,3),3)&(al>40)`。
2. **文字带 `textbox(m)`**：取**行宽 ≥ 0.55×峰值的最长连续段**。早期「峰值行向外扩展」的版本会把 next / worldmap / save_me 裁错。实测：btn_next_normal (41,19,179,36)、btn_worldmap_normal (20,17,181,40)、btn_save_me_normal (5,70,260,131)、btn_upgrade_normal (0,60,98,83)、btn_shop_normal (1,5,85,74)。
3. **擦除 `laplace_fill(a,m,iters=260)`**：先 `out[m]=median(rgb[valid])`，再迭代 `nb=(roll(-1,0)+roll(1,0)+roll(0,-1)+roll(0,1))*0.25; out[m]=nb[m]`，`oa[m]=max(oa[m],255)`。淘汰过：归一化卷积、row_lerp+col_lerp 平均、spread_fill、cc_bbox_fill、band 外取样 refs。

帧分四类：`T` 纯文字帧（alpha 清零后整帧重绘）、`B` 按钮帧（擦字 + 带内重绘）、`I` 图标帧（硬编码 `ICON_BAND` + 暖色掩码 `core=bm&(R-B>45)&(R>110)&(al>60)`）、`G` 金色帧（`gold_mask=(R>195)&(G>165)&(B<130)&(al>60)&((G-B)>85)` + `lerp_fill` 双向插值；奖章是放射渐变，调和插值会把中心抹平）。

中文绘制 `draw_cn`：`<WORKSPACE>\Fonts\msyhbd.ttc`，32 轮二分求最大可用字号（`hi=max(8,min(int(bh*2.4),320))`），描边 `max(1,round(size*0.11))`，先描边层再 fill 层（渐变 top→bot=top*0.82）；rotated 帧取 `crop((x,y,x+h,y+w)).transpose(ROTATE_90)`，回写前 `transpose(ROTATE_270)`。

**有意保留英文的两帧**：`start_title`（NYANKO NINJA logo）、`free_coin_main`（蓝色三角旗，行剖面是斜三角没有文字带）。

**踩坑**：`_gen.py` 的 `MAP` 组装顺序极易被字符串 replace 打乱（会 `NameError: name MAP is not defined`），改脚本要整段重写。改完必须重跑 `_grid5.py` / `_cmp_all2.py` 逐帧目视对照，不能只看 saved 字节数。

### 16.2 文本层：三条消费路径

引擎字体是 BMFont（`wyBitmapFont`，无 FreeType）。`_ZN12wyBitmapFont11measureTextEPKciff @0x80960` 把 UTF-8 字节用 `lsls r4,r4,#8 / orrs r4` 组装成 Unicode 码点，再 `bl _ZN12wyBitmapFont11getCharInfoEi @0x80954` 查表 —— 只要 fnt 里有该码点就能渲染中文。字体加载器字符串在 `libwiengineskeleton.so` 0x1131c4 起（WyAngelCodeTXT/XMLFontLoader，另有 wyHGEFontLoader 0x113394），**无 scaleW/scaleH 字符串，纹理尺寸由 PNG 本身决定**。

同一个英文串可能被三种方式消费，必须分清，否则白改：

| 路径 | 特征 | 处理方式 |
|---|---|---|
| `.data.rel.ro` 指针槽 | 槽值落在 `.rodata`，`_slots_all.json` 里有 | 改槽指向中文串（零字节风险） |
| 硬编码地址直读 | 改槽后界面仍显英文，且该串在 `.text` 里无 dword 字面量引用 | **就地覆写原串字节** |
| 资源键 | 引擎归一化（小写 + 空格转下划线）后拼资源名查 APK | **绝不能改**（见 16.6） |

元素名（Water/Wind/Fire）、`Quest complete`、`Attack`/`Defence`/`HP`、`Duration`/`Illusion(s)`、飞镖名、`Bamboo Grove`/`Highest Score` 都属于第二类：改槽无效，必须就地覆写。

### 16.3 指针槽表 `<WORKSPACE>\out\_lang\_slots_all.json`

`.data.rel.ro`(0xf0b40..0xf0b40+0x981c) 每 4 字节扫、值落在 `.rodata`(0xdc9d0..+0xcf3c) 的全部槽共 **1227 个**（含空串槽）。字段 `{i, off, v, s}`，`off`/`v` 是十六进制字符串，读时必须 `int(x,16)`。

**中英块完全同构**（整套方案的地基）：技能区 0xf0b40 起 12 技能×4 槽（名/长描述/短格式/长描述2），第二副本 0xf0f78 起同构；元素 0xf0c00–0xf0c10 与副本 0xf0f64–0xf0f74；成就描述 CN 0xf0c14–0xf0c98 / EN 0xf0c9c–0xf0ce0；成就名 CN 0xf0d2c–0xf0db0 / EN 0xf0dbc–0xf0df8；第二副本 0xf1750–0xf181c；飞镖/服装/头盔名与描述 CN 0xf0dfc–0xf0f38 + 日文 + EN 0xf0e24–0xf0f60；怪物名 CN 0xf1038–0xf109c / EN 0xf1110–0xf1174；怪物描述 CN 0xf117c–0xf11e0 / 日文 0xf11e8–0xf124c / EN 0xf1254–0xf12b8；教程 UI CN 0xf1438–0xf1530 / 日文 0xf1544–0xf163c / EN 0xf1644–0xf174c。

所以大量条目**不用写中文**，把英文槽指向既有中文串即可；`_tr.py` 只有 122 条译文，实际做法是「槽重映射为主 + 少量自写串为辅」。

三个注意点：①`%.0f%%`(0xdde68) 与 `%.1f%%`(0xde1d0) 是**多技能共用**短格式串，禁止改指；②怪物描述 26 槽里有 12 个指向空串 0xe391c，平移时必须跳过；③`0xdffb0` 的 `Level Design` 是 staff 名单里的名字，与 `0xe046c` 的关卡横幅 `Level` 同名，改错会把制作名单变成「关卡设计」。

### 16.4 扩区写新串（PT_LOAD#1 扩展）

`.rodata` 里 ≥8B 的零区共 84 段合计仅 1469B，装不下新译文。`0xee60c..0xf0a20` 共 **9236B 全零**，原本不在任何 PT_LOAD 内。把 `PT_LOAD#1` 的 `p_filesz`/`p_memsz` 从 0xee60c 改到 0xf0a20 即把它纳入映射。

b187 单变量验证：与原始 so 的差异只有 `0x64/0x65/0x66`（filesz）与 `0x68/0x69/0x6a`（memsz）六个字节，真机正常出图、无副作用、无崩溃。**坑**：用 `type==1` 遍历程序头会同时命中 LOAD#2(off/va 0xf0a20)，必须 `type==1 and vaddr==0 and off==0`。

写入器从 0xee60c 顺序写 UTF-8+NUL、4 字节对齐，`sk_final.so` 用掉 1112/9236 字节。

### 16.5 就地覆写的两条硬规则

1. **跨度按「到下一个非空串起点」算**，不是「到下一个原始串起点」（中间常有连续 NUL 填充）。例：`Back`/`Reset`/`Enter`/`Tips:` span=8（可容 2 汉字）、`Go!`/`Set`/`OK`/`MAX` span=4（只能容 1 汉字）。
2. **覆写区间不得包含任何被引用地址**：`clash = any(a < w <= a+len(zh) for w in ALLV)`，ALLV = 全量槽目标 ∪ `.data.rel.ro` 内所有落在 `.rodata` 的 dword。

第 2 条是血换来的。b159 把 `Unlock any element`(0xde9c4) 覆写成 18B 中文，正好盖到 0xde9d4 的残片串 `nt`（被槽 0xf1e20 引用），引擎读到非法 UTF-8 → GLThread 100% CPU 空转 → **全黑屏且无 FATAL、无 SIGSEGV**。b160（只换 2048 字体）正常、b161（只换全量 so）黑屏，据此把成因从字体剥到 so。黑屏判据：`screencap` PNG < 60KB + `top -H -p <pid>` 里 GLThread 满 CPU。

另一个坑：**相邻短串的就地覆写会互相踩**。0xde73c `New Journey` 与 0xde748 `Newbie of Element` 紧邻，前者译文写进去正好被后者覆写盖住。注入时要额外排除「另一条待注入串的起点落在本串覆写区间内」的情况。

### 16.6 闪退定案：`Fire Fury` 是唯一资源键

全量注入后进关卡必崩，崩溃栈（`logcat -b crash`）：

`Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x00000000`，`Cause: null pointer dereference`

`#00 libc.so (strtod+46)` ← `#01 libwiengineskeleton.so (MainGameLayer::loadMap(int)+1362)` ← `#02 MainGameLayer::MainGameLayer(int,bool)+272` ← `#03 MainScene::MainScene(int,bool)+220` ← `#04 LoadingScene::loadingThreadEntry(...)` ← `#05 libwiengine.so wyTargetSelector::invoke()`。崩溃在**加载线程 Thread-8**，不是 GLThread。

静态反汇编追不到键名（`0x7a6e4 add r2,pc` 指向 0x7b12c，那里是 ARM 代码字节不是字符串；strtod 入参来自 `ldr r0,[r4,#0x4c]` 这类对象成员），只能动态二分。逐档二分定位到 **0xe3c04 `Fire Fury`**：

| 包 | 改动 | 结果 |
|---|---|---|
| F1 | 0xe3c04 → `豪火球`（9B 等长中文） | **闪退** |
| G1 | 0xe3c04 → `FireFuryX`（9B ASCII） | **闪退** |
| H1 | 0xe3c04 → `FireFury `（尾空格 9B） | **闪退** |
| G2 | 0xe3c04 → `Fire fury` | **正常** |
| G3 | 0xe3c04 → `Fire_Fury` | **正常** |
| H2 | 0xe3c04 → `fire fury` | **正常** |

结论：**与编码、长度无关**。该串被当资源键，引擎归一化（小写 + 空格→下划线）得到 `fire_fury` 去查 APK 资源（包内确有 `res/drawable/fire_fury.png`、`res/raw/fire_fury.sprite`）；命中失败返回 NULL → `loadMap` 把 NULL 交给 `strtod` → 段错误。只要能归一化成 `fire_fury` 就崩，所以 `Fire Fury` 必须逐字节保留（对应训练师页那一项只能显示英文），其余 56 条就地覆写全部实测安全。

**方法论教训**：`input tap` 在非当前界面会被静默丢弃，会出现「以为没崩其实是根本没进关卡」。判崩溃必须同时满足 `pidof` 为空 **且** `logcat -b crash | grep -c 'Fatal signal'` ≥1。
